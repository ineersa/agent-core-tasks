## Goal

## Existing evidence

Read [the investigation report](../reports/2026-09-25-messenger-worker-performance-investigation.md). Its inspected baseline is fb4096b6537883246b93c0f46b71b7575690d391. Recheck current code before implementation.

- ConsumerSupervisor passes --sleep=0.01. This is an idle polling interval, not a guaranteed pickup latency. Busy workers, scheduling, database contention, admission, approvals, and output delivery can add time.
- LlmStepResultHandler emits ToolExecutionStart for every effect before batch admission and worker dispatch. The live timer starts there, while ordinary completed duration_ms measures executor-side work. These intervals differ.
- ToolDurationHeaderWidget renders immediately and ticks once per second, using milliseconds below one second and whole seconds afterwards. A unit change alone is not evidence of delay or serialization.
- ReadFileTool and BashTool both register parallel execution. ToolBatchCollector admits eligible calls up to maxParallelism and preserves sequential barriers. An independent read+bash pair should be investigated through the native multi-call path, not confused with sequential code_mode calls.
- Results can complete independently, while model history is committed in assistant order after batch completion. Transcript order is not a concurrency measurement.
- MCP calls and code_mode nested calls are separate intentionally serial paths. They are controls, not evidence that generic tool messages serialize.

## Investigation and implementation scope

1. Reproduce an independent native read+bash batch on the current runtime with test-owned resources. Trace the actual model-call representation, registered modes, admission, queue routing, worker entry, tool completion, run_control result commit, controller delivery, and TUI visibility. Also inspect a fast standalone read, an occupied tool pool, and a slow sibling with a fast sibling. Distinguish an approval wait from worker starvation.
2. Build a correlated timeline using existing IDs and observability. Separate admission wait, queue wait, execution, result processing, and display delay. Prefer existing structured logs and runtime events. Add only the smallest missing evidence needed to locate a demonstrated problem, not a general metrics subsystem or speculative persistence schema.
3. Prove real overlap independently of visual ordering. If eligible calls serialize, identify and fix the first serial boundary. If execution already overlaps, fix any demonstrated admission, delivery, or presentation delay instead. Never infer serial execution solely from the timer or card order.
4. Correct the existing timer semantics so queued work is not falsely described as executing and the live/final label does not silently change the interval it represents. Preserve deferred subagent lifecycle timing. Audit failures, cancellation, direct shell, human-input suspension, and background handoff. Finalize any additional visible queued label or formatting preference before introducing it. The earlier whole-seconds-live proposal is not yet a finalized product requirement.
5. Fix only measured bottlenecks in the current architecture. Keep consumer counts, transport choice, execution modes, and dependency versions unchanged unless concrete findings establish a separately approved need. Do not reduce the 10 ms poll interval blindly or raise worker counts to conceal the cause.
6. Record before/after phase timings and the remaining limitations in the report. State whether generic tool concurrency was broken, whether only its display was misleading, or whether both were affected. Reassess the need for an upstream pool from these results rather than scheduling an automatic migration.
