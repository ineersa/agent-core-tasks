# Improve unified-diff edit tool feedback and safety

## Goal
## Context
Hatfield's current `EditFileTool` applies unified diffs via GNU `patch` with a dry-run first, then writes patched output to a temp file and renames it over the target. Success output is concise and does not echo the full diff, which is good for token usage. However, temp-file rename can replace symlinks and break hard-link identity.

Failure output currently mostly forwards GNU patch stderr/stdout with generic hints. Example shape:
- `Patch dry-run failed for "...": <patch output>`
- hint: `Check that the patch context matches the file content and the diff is in unified format.`

This is actionable-ish but often not enough for the model. GNU patch may only say `Hunk #1 FAILED at 42`, without showing the current file context needed to retry.

## Goal
Improve model-visible edit failure feedback, prompt/tool guidelines, and link-preserving write behavior for the existing unified-diff edit tool, without switching to hashline and without returning full applied diffs on success.

## Suggested improvements
- Switch the apply path from temp-output + rename to dry-run + locked in-place patching where feasible: `patch -u -F3 -l -N target patchfile`.
- Use Symfony Lock around the edit critical section before applying in-place changes.
- Preserve symlink and hard-link behavior: in-place patching should follow symlinks to their target content and preserve hard-linked inode identity so other hard-linked names see the edit.
- Accept the explicit tradeoff: in-place patching is not rename-atomic. This is acceptable for this task; most real usage has git as backup/recovery.
- Add best-effort rollback for normal patch application failure/cancellation if practical: snapshot original bytes before in-place apply and restore them in place on failure. Do not use rollback rename that would reintroduce link breakage.
- On dry-run/application failure, parse failed hunk locations from GNU patch output, e.g. `Hunk #1 FAILED at 42`.
- Include a small bounded current-file context window around failed line numbers in the tool error, e.g. ±3 to ±5 lines with line numbers.
- Keep error output concise and token-bounded; do not dump entire files or full patch content.
- Normalize failure codes/messages for LLM retry behavior, e.g. `[E_PATCH_FAILED]`, `[E_PATCH_FORMAT]`, `[E_PATCH_NOOP]` if appropriate.
- Distinguish common causes when detectable:
  - malformed unified diff/header;
  - stale context/hunk failed;
  - target file has no trailing newline;
  - reversed/already-applied patch (`patch -N` may skip);
  - permission/temp-file/write failure.
- Improve `definition()` prompt guidelines for unified diff generation:
  - read current file first;
  - use exact current context lines;
  - keep hunks tight;
  - include enough unchanged context for patch matching;
  - do not echo full applied diff in success expectations;
  - if an edit fails, retry from returned current context.
- Preserve success response compactness: continue returning only path + addition/deletion stats by default.
- Consider host-only details for UI/debugging if the tool result plumbing already supports it; model-visible text should remain compact.

## Safety/robustness notes
- Do not broaden this task into hashline or a new edit schema.
- Do not add fuzzy relocation beyond GNU patch behavior in this task.
- Prefer preserving symlink and hard-link semantics over rename-style atomic replacement for existing files.
- Document the tradeoff clearly in code comments: dry-run + in-place apply preserves links/inode identity, but cannot provide the same crash atomicity as temp-output rename.
- Keep existing comments explaining the two-pass patch lifecycle updated if behavior changes.
